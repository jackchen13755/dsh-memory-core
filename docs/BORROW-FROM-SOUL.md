# 从 dsh-soul 借鉴什么、拒绝什么（2026-10-29）

评估对象：[dsh-soul](https://github.com/icyaaaww/dsh-soul)（DSH 插件，主打「记忆骨架 + 图压缩 + 经验编译」）。
本文只讨论**能移植到 dsh-memory-core 的部分**，不讨论要不要装那个插件本身。

先给结论：**值得借的只有 4 项，且没有任何一项是照抄**。其中收益最大的一项不是新功能，而是借它的一条原则
去修我们自己的一个正确性 bug。

边界先说清楚（这三条决定了下面每条判定的取舍方向）：

- 收益面：每条机制必须为「注入质量 / 队列质量 / 成本」三者之一服务，否则不借；
- 成本面：不得破坏三条既有硬契约——零直写（`extract.js`）、常驻 token 预算（`inject.js`）、快照往返字节一致（`snapshot.js`）；
- 证据面：dsh-soul 公布的基准数字只能当**方向**，不能当**预算依据**（理由见 §4）。

## 2. P0：一个能复现的正确性 bug（借的是原则，不是代码）

**现象**：`reinforce` 每轮巡演用 `since = now - 72h` 重扫整段 `recall_log`，然后对每条命中执行
`importance += 0.08 × min(3, hits) × (injected ? 1.5 : 1)` 与 `access_count += hits`，**没有任何消费水位**。
而 `runEvolution` 每 30 分钟巡演一次 → 同一条激活在 72 小时窗口内最多被重复计入 **约 144 次**。

**后果是连锁的**：

1. importance 迅速撞到 `maxImportance` 上限，权重退化成「取回过 / 没取回过」的**二值**，排序信号失效；
2. `access_count` 同比例虚高；
3. 而 `decay` 的免归档宽限（`access_count > 0` 就不归档）与 `reviveArchivedBoosted` 的两个判据，
   读的正是这个虚高值 —— 于是「是否被取回过」这个判断在最该准确的场合最不可信。

**修法**：`meta.evolve_reinforce_rowid` 作为消费水位，只消费新行。

**为什么用 rowid 而不是 ts**：同一毫秒内会批量写入多条检索归因，用 ts 做 `>` 会漏掉同毫秒的新行，
做 `>=` 又会重复消费边界批次。rowid 单调递增且与写入顺序一致，无此问题。
窗口条件保留（`ts >= since`），避免升级后一次性补算陈年日志。
水位在 `COMMIT` 之前写入，回滚则水位不动 —— 失败重试不会重复计价。

回归测试：`test/evolution.test.js` → 「强化消费水位：同一条激活跨多轮巡演只计一次」。
这个测试在修复前必然失败。

## 3. 已实施的三项能力

### 3.1 会话状态骨架（P1-1）

**补的洞**：压缩之后「这轮到底定了什么」没有任何恢复路径。

- 常驻段只放 `rule` / `preference`（`inject.js` 的 `RESIDENT_KINDS`）；
- 按轮卡片是 **query 驱动**（用本轮用户消息检索）。

于是「我们决定用 anchor 而不是摘要，因为摘要会丢约束」这类**决策**：它不是规则，也没有任何 query 能命中它。
压缩一擦，就再也捞不回来。（`mem_recall` 能救，但前提是模型意识到自己丢了东西 —— 而它常常意识不到。）

**实现要点**：

- `lib/skeleton.js`：零模型调用的机械抽取，显式词表，三类节点 `constraint` / `decision` / `progress`；
- 触发点：`agent/turn-stopping`（宿主已文档化、本插件早已订阅、按回合关闭触发一次）；
- 注入：独立段 `memory-core:skeleton`，**order 605**（夹在常驻 600 与按轮 610 之间），
  独立预算 **220 token**；
- 投影是**全序确定性**的：排序键 = pin → kind 秩 → content_hash → id。

**四个刻意的取舍**：

1. **不并入规则段**。规则预算是 600，状态若挤进去，等于用新机制的失败换旧机制的失败。
2. **不抽 `artifact` 节点**。它的价值在「失效判定」（§3.4），先抽只会在投影里堆「文件已写入」这类噪声。
3. **只在 turn-stopping 收口一次**，不挂 `tools/post-execute`。那个瀑布在工具链里被 await 且**没有内建超时**，
   监听器抛错会把该次工具结果变成 `isError` —— 为一个旁路统计冒这个风险不值得。
4. **图空发空串**。新会话零成本，历史会话不付固定税。

**为什么必须确定性**：`systemPrompt.context` 的 text 每步求值，宿主按内容比对，只有变化才追加运行时快照。
投影若随权重漂移（比如把 importance 放进排序键），就会每轮抖动、每轮追加，比不做还差。
确定性要成立，**排序键和集合选取都必须全序**：`nodeLines` 是全序（pin → kind 秩 → content_hash → id），
`loadNodes` 与 `pruneNodes` 的 `ORDER BY` 也必须带 `id` 兜底 —— 同一次 upsert 写入的节点
`created_at` 完全相同，没有兜底时「选哪几条」由实现细节决定。

两处评审后修正的取舍：

- **不在 SQL 层按条数静默截断**。第一版 `loadNodes` 带 `LIMIT 24`，实测 30 条 pin 约束只进去 19 条，
  其余既不显示也不报数——等于用新机制复刻了它本来要修的洞。第二版改成 `LIMIT 192`，
  评审用 250 条证明**只是把阈值挪远**（仍丢 58 条且不计数）。
  现在默认取全量，只留 `SAFETY_CAP = 1000` 防病态数据，且真碰到会把 `truncated` 报出来计入 `dropped`。
  token 预算才是约束，条数不是。
- **精度优先要落到来源上**。真实会话实测（6 个会话、`maxMessages=20`）：抽出 26 个节点里
  **24 个来自助手**（92%），混着「接下来测试边界」这类过程自述和 JSON 碎片，
  而这些碎片会因为命中「必须」被置成 `pin=1` 的永久约束。
  现在：**约束/决策只从 user 消息抽**（人定的规矩，助手复述不算），进度两个来源都要但助手来源不置 pin。

对照：常驻段现有的 `ORDER BY pinned DESC, importance DESC` 就有这个隐患 —— importance 被 `reinforce` / `decay`
持续改写，同一 DB 在不同时刻渲染结果不同。本次**没有改它**（超出范围），但已记录为已知项。

### 3.2 三类节点而非四类

`constraint` 置 `pin=1`：投影时优先，`pruneNodes` 不删。这是 dsh-soul 那条 `pin=1` 的等价物，
但 memory-core 本来就有 `pinned` 列 + 规则/目录独立预算 + decay 对 pin 的豁免，所以**没有**再造一套 pin 语义。

### 3.3 支持度计数（P1-2）

**问题**：`sweepSuggestions` 是 14 天一刀切，于是「用户纠正了三次的事」和「一次性噪声」在队列里**完全同权**。

**改法**：

- `store.insertSuggestion`：再次写入时 `support += 1`、刷新 `last_seen_at`，不产生第二行；
- `listSuggestions`：`ORDER BY support DESC, created_at DESC`；
- `sweepSuggestions`：**两档宽限**。普通建议 14 天归档；`support >= 3` 的给 90 天
  （按 `last_seen_at` 算，即「最近还在被提」）。

**两个必须记下来的坑**（都是评审实测出来的，第一版都错了）：

1. **去重键不能含易变字段**。第一版用整个 `payload` 派生 id，而 payload 里有 `origin`
   （`session:<id>#<seq>`）、`cwd`、`relation.candidates`（实时检索结果的浮点相似度）。
   结果「同一句话第一次在 A 会话提、第二次在 B 会话提」得到两个不同 id，各 `support=1` ——
   而这正是支持度最该覆盖的场景，功能在真实路径上等于空转。
   现在收窄成 `kind + target + sha1(主体文本)`：内容和轨道相同就是同一件事。
2. **达标不能等于永久免疫**。第一版写成 `support >= 3` 永不归档，结果队列烂尾换个形式回来。
   现在是「更长的宽限期」，连它也有第二道时间闸。

### 3.4 产物失效指纹（P2-1）

**问题**：`units.content_hash` 只是**内容去重指纹**（同内容不重复入库），并不表达
「这条记忆所指的外部文件是否还在」。记忆里写着 `lib/schema.js:54 的 edges 表`，而那文件后来被改了，
这条记忆仍会被召回，但它的证据已经作废。

**实现**：`lib/artifacts.js` 从正文抽候选路径 → 留 sha1 → 后台巡演核对，
状态写在 **meta 表**（`artifact:<unitId>`），**不写 `units.meta`**。

五条硬约束（前三条是第一版就写下的，后两条是评审补上的）：

1. **advisory only**：不改 importance、不改 status、不归档、不删除。「判定失效」是给人看的信号，
   不是删除授权（对齐 `decay` 的「只归档不删除」）；
2. **不进检索热路径**：只在 30 分钟一次的后台巡演里跑，召回 p95 预算 12ms 不能被磁盘 I/O 污染；
3. **相对路径默认不判**：没有 cwd 就只核对绝对路径与 `~/`。跨设备路径对不上是常态，宁可不判也不误判；
4. **不写同步列**（评审补）：`units.meta` 是 sync 的整列替换载荷，写进去会把「A 设备的绝对路径 +
   文件哈希」同步到 B 设备，B 下一轮全部重基线、期间的真实漂移被静默接受。状态一律放 meta 表；
   而 `nodes` / `node_edges` 同理不进 `ENTITIES`。**派生状态不能搭同步的车。**
5. **路径要有栅栏**（评审补）：记忆正文来自模型写入，等于模型能决定插件去 stat/读哪个文件。
   所以：只核对待核根目录内（home / cwd）、`lstat` 拒绝软链、跳过敏感目录
   （`.ssh` / `.aws` / `.gnupg` / `.env` / `credentials` / `Keychains` / `.npmrc`）、
   单文件 ≤256KB、每轮总读取 ≤8MB。

另外两处**必须有消费方**才算功能完成（评审意见：只写不读不等于功能）：

- 统计进 `mem_status`（`产物证据：N 条已建指纹 · X 条内容已变 · Y 条所指文件已不在`）；
- 轮转核对：按稳定的 unit id 排序 + OFFSET 推进，1000+ 条的库最终都能被覆盖，
  而不是永远只查「最近 60 条」。
- 无哈希用**哨兵值**（`MISSING` / `SKIP`）而不是 `null`：第一版用 `null` 表示"没哈希"，
  于是「首轮就缺」和「超大文件」会永远走"没见过"分支、永远报 ok ——
  恰恰是这个功能最该发现的两种情形被静默吞掉。

**诚实说明一处局限**：首次核对是**建立基线**（记当前内容），不是「写入时内容」。也就是说，
如果文件在第一次核对之前就已经变了，这次不会被发现。要做到真正的「写入时指纹」，需要在写入路径上落指纹 ——
那会让 `writeMemory` 多一次磁盘 stat，本次刻意不做。

### 3.5 `mem_recall` 两层回捞（P2-2）

第一层查会话骨架节点及一跳邻居；命中不足 2 条时，第二层自动翻会话原文（`readTranscript`：活体优先、落盘兜底），
每条结果标 `source=node` 或 `source=span`。

**只做显式调用**，绝不挂进自动注入路径 —— 按轮自动翻原文会直接违反「per-turn ≤400 token」与
「`missedStreak ≥ 5` 主动停」这两条既有省 token 设计。

## 4. 明确拒绝的部分（以及为什么）

### 4.1 机械抽取替代 / 前置 LLM 会话提取 —— 拒绝

三条理由，任何一条都足以否掉：

1. **确认队列的成本 100% 由误抽主导**（人工工时花在「这条不该记」上），
   而 dsh-soul 从头到尾**没有度量过一次 precision**。它的 79.1% 是「召回留存」，不是「抽对了」。
2. **数量级不对**：本插件一次会话提取上限 `maxItemsPerRun: 8`（`extract.js`），全会话一次；
   按轮机械抽取是 O(轮数)，一个 60 轮会话会产生几十条候选 —— 要么破零直写，要么把队列淹掉。
3. **破坏零直写**（这是用户明确的硬要求）。

而且它恰好在 memory-core 最值钱的那类长尾上最弱：`kind=env`、工具用法、路径类事实
（dsh-soul 自己的基准里，只出现在工具输出里的 2 条环境事实，骨架只拿到 17.7% 和 0%）。

### 4.2 shadow / 成对验证 / 版本树 / 回滚链 —— 拒绝

本插件的「编译」产物是记忆条目，闸门已经是**人工确认** —— 比 shadow 更强、更便宜、不烧 token。
再叠一套版本树 + 成对重跑是给已有闸门加机械闸门（架构航天）。
而且 `eval/labels.json` 只有 24 条，统计功效不足以支撑「每一组都要赢」。

### 4.3 每轮命中不足自动翻会话原文 —— 拒绝（改造为显式工具）

见 §3.5。

### 4.4 把节点图当第二事实源 / 允许直接编辑节点 —— 拒绝

会造出「双写 + 同步冲突 + 快照不可判定」。`nodes` / `node_edges` 是**会话级派生态**，与
`units_fts` / `vectors` / `edges` 同级：丢了能从会话重算。具体三条硬边界：

- **不进 `sync.js` 的 `ENTITIES`**：会话内状态同步没意义，还会造伪冲突；
- **不进 Markdown 快照**：那会动 `bin/mem.js verify` 的字节比对基线，把一条已通过的验收变成不可判定；
- **不进 `suggestions`**：那是「会话结束时 LLM 判定值得长期保留」的语义，灌进按轮节点会让它变成
  「这轮干过的事」，还会破坏「面板只显示本会话」那条用户明确要求过的过滤。

节点要升成长期记忆，只有一条路：`writer.approveSuggestion`（带 `origin`），
那条路自带去重、敏感信息扫描与提示注入筛查。

### 4.5 「5 倍保留率」这个数字不能当依据

README 写「机械抽取的保留率是模型摘要的五倍（Compact-Bench：79.1% vs 16.0%）」。
但 `docs/SKELETON-BENCH.md` 里**根本没有这一对数字**，同预算的合法对照是：

| 预算 | 窗口截断 | 摘要替代（自述**非 LLM**） | 骨架 |
|---|---|---|---|
| 600 | 15.3% | 16.7% | **45.5%** |
| 1200 | 25.5% | 43.2% | **83.4%** |
| 2400 | 41.1% | **86.8%** | 84.1% |

三点必须同时看到：

1. 1200 字节时是 83.4% vs 43.2% = **1.9 倍**，不是五倍；
2. 2400 字节时**均匀采样反超骨架**（86.8 vs 84.1）—— 优势来自压缩比，不是绝对质量；
3. 这个指标测的是「记忆项的字面量是否还在上下文里」。机械抽取的工作方式就是照抄字面，
   摘要的工作方式是改写 —— 一个完美摘要器在这个指标上天然吃亏。作者自己在文档里也写了
   「83.4% 里有一部分是『抽取对了』而不是『选对了』」。

**它能支撑「机械抽取在被压狠的场景值得一试」这个方向，但不能支撑任何预算决策。**
本文所有预算（220 token）都是按本插件自己的口径定的，不是从 dsh-soul 抄的。

## 5.1 评审发现并已修（第一轮代码审查 + 验收）

第一版交付时 250 项测试全绿，但两位专家各跑了一套探针，独立复现出 3 个 blocker、10 个 major。
**最严重的一条是"测试绿但功能从未生效"**，值得单独记下来：

| 缺陷 | 为什么会漏过测试 | 现在 |
|---|---|---|
| `verifyArtifacts` 调用点传参形状错（`verifyArtifacts({store})` vs `(store, opts)`），`runEvolution` 每轮静默抛错、被 `guard` 吞掉 | 测试只直调函数本体，**没测调用点** | 修签名 + 新增「跑完巡演必须真的写下状态」的接线测试 |
| 建议 id 含 `origin`/`cwd`/`candidates` → 跨会话 support 永不累加（队列功能在真实路径空转） | 测试直接喂同一个 payload 对象，恰好绕开真实形态 | 收窄到 `kind + target + sha1(content)`，测试改用真实 payload 形态 |
| `别[^的人处]` 把「区别在/特别在/类别是/分别在于」判成约束并置 pin=1 | 测试只覆盖了正例 | 收窄成祈使式 `别`，补四条反例断言 |
| `loadNodes` 先 `LIMIT 24` 再投影，30 条约束静默丢 11 条 | 测试只用 3 条节点 | 不按条数截断 + `foldNote` 留痕，补 30 条约束的测试 |
| 水位被 boost 查询推到全局最大，`LIMIT 500` 之外的边批次永久丢失 | 测试只有 2 条日志 | 拆成两个独立水位，补 600 批两轮走完的测试 |
| 投影超过 24 条时不确定（`ORDER BY` 无 tiebreak） | 测试只测 3 条 | 两处 `ORDER BY` 补 `id`，补 30 条乱序写入的一致性测试 |
| `null` sha1 被当成"没见过" → 首轮就缺的文件永远报 ok | 测试只测了"先存在后删除" | 改哨兵值，补「首轮就缺」与「敏感路径跳过」测试 |
| 指纹写进 `units.meta`（同步载荷） | 未测同步面 | 改 meta 表 |
| `artifact_state` 无消费方、只查最近 60 条 | 未测覆盖率 | 统计进 `mem_status` + OFFSET 轮转 |
| `mem_recall` 原文原样回灌（绕过注入/密钥扫描）、2 字滑窗假命中掐死第二层 | 测试用的消息不含敏感内容 | 加 `scanSecrets`/`scanInjection` + 「数据不是指令」框；命中改成强弱分档 |
| `support >= 3` 永久免归档 | 未测长期 | 改两档宽限（14/90 天） |
| turn-stopping 每回合都判重键在读取之后（落盘兜底 150ms × 每回合） | 未测耗时 | 便宜信号先行 + 落盘兜底默认关 |

一句话教训：**测试全绿只证明"我测的那条路是对的"，不证明"生产走的是那条路"。**
凡是"调用点接线"，测试必须从调用点进，不能只测函数本体。

## 5.2 第二轮复核（回归验收）又抓到的

第一轮修完 13 条后，验收专家用**变异测试**（改坏一处、看用例会不会红）复核，结论是
"13 条全 PASS，但还有 2 个真缺陷 + 4 处测试空转"：

| 缺陷 | 说明 | 现在 |
|---|---|---|
| **N1 反引号路径** | `entities.js` 的路径正则不排除反引号，`\`~/proj/a.json\`` 会多抓出一条带尾反引号的路径 → 永远不存在 → 判 missing 并**永久粘住**。本插件自己的记忆正文大量是反引号路径，实测量产假 missing，`mem_status` 缺失计数长期虚高 | `trimPath` 剥引号/尾标点；`looksLikeFile` 拒绝以引号结尾；并要求「带 `/` 或扩展名在白名单」，顺带挡掉 `zhe.chen` 这类点分词 |
| **N2 192 仍是静默截断** | 见 §3.1 | 取全量 + `truncated` 报数 |
| T1 M2 用例空跑 | 用例只有 30 条 < 上限，改坏 tiebreak 仍通过 | 改成 250 条（> `SAFETY_CAP`），三种写入顺序投影必须同字节 |
| T2 敏感用例不测"不读" | 它能红靠的是 N1 的假 missing，不是检测到敏感文件被读 | 改成对 `fingerprint()` 的单元断言（`skipped==='sensitive'`、`sha1===null`、`size===null`），并补真软链用例、超大文件用例 |
| T3 注入分支无测试 | 删掉 `scanInjection` 判断测试照绿 | 补「高危注入原文不回灌」用例 |
| T4 fakeSession 事件形状错 | 助手事件写成 `data.content`，而生产取 `data.message` → 测试里助手消息被**静默丢弃** | 按生产形状构造，并补「助手消息真的能被回捞」用例 |

另外补齐了评审点名"无机器验证"的几条：`artifactCwd` 默认值与配置接线、
`nodes`/`node_edges` 不进 `ENTITIES`、`mem_recall` 拒绝非当前会话 id、轮转真的覆盖全库。

**N1 这条最值得记**：它让一个健康记忆被永久标成"证据已失效"，而这是该功能唯一的输出信号。
根因不是算法，是**字符串清理没做干净**——加一个功能时，最容易漏的是"输入从哪来、会不会带装饰字符"。

## 6. 一句话总结

**借的是四条原则**：activation 只消费一次、状态要有独立且确定性的投影、
反复出现的事该有支持度、产物证据会过期。
**不借的是两套体系**：用机械抽取替代人工闸门、用一个还没验证的基准去决定 token 预算。
